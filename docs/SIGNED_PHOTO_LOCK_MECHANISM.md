# 签字照片锁定机制与责任区分

## 📋 需求背景

> "这个照片需要一个更换删除的选项然后在为了责任区分在我们的维修人员开始查看以后禁止修改照片如需修改去要申请"

---

## 🎯 核心目标

1. ✅ 现场人员可以删除/更换照片（维修人员查看前）
2. ✅ 维修人员查看后自动锁定照片
3. ✅ 锁定后禁止现场人员直接修改
4. ✅ 需要修改时走申请审批流程
5. ✅ 明确责任归属，防止纠纷

---

## 🔒 锁定机制

### 触发条件
```
维修人员打开打印/查看报告页面
↓
系统检测到签字照片存在
↓
自动延迟2秒后记录查看
↓
照片立即锁定
↓
现场人员无法再修改
```

### 为什么延迟2秒？
- 给维修人员时间看到照片
- 避免误触发锁定
- 确保是真正的查看行为

## 🔧 API 端点

### 1. 记录查看（自动锁定）

**端点**：`POST /api/tickets/signed-photo/[batchId]`

**权限**：仅维修人员（Technician）

**功能**：记录维修人员查看签字照片，自动锁定

**请求**：无需body

**响应**：
```json
{
  "success": true,
  "message": "查看记录已保存",
  "data": {
    "viewedBy": "TECH001",
    "viewedAt": "2026-02-24T14:30:00.000Z"
  }
}
```

**数据库操作**：
```sql
UPDATE Repair_Tickets
SET 
  SignedPhotoViewedBy = @viewedBy,
  SignedPhotoViewedAt = @viewedAt
WHERE BatchId = @batchId
AND SignedReportPhoto IS NOT NULL
```

---

### 2. 删除照片

**端点**：`DELETE /api/tickets/signed-photo/[batchId]`

**权限**：仅现场人员（Reporter）

**功能**：删除签字照片（仅未锁定时可用）

**验证**：
- ✅ 检查是否为现场人员
- ✅ 检查照片是否存在
- ⚠️ 检查是否已被查看（锁定）

**成功响应**：
```json
{
  "success": true,
  "message": "签字照片已删除"
}
```

**失败响应（已锁定）**：
```json
{
  "success": false,
  "message": "签字照片已被维修人员查看，无法删除。如需修改请申请。"
}
```

**数据库操作**：
```sql
-- 1. 删除服务器文件
unlink('public/uploads/signed-reports/xxx.jpg')

-- 2. 清空数据库字段
UPDATE Repair_Tickets
SET 
  SignedReportPhoto = NULL,
  SignedPhotoViewedBy = NULL,
  SignedPhotoViewedAt = NULL
WHERE BatchId = @batchId
```

## ⚖️ 责任区分

### 为什么需要锁定？

**场景1：避免纠纷**
```
维修人员根据签字照片开始维修
↓
现场人员事后更换照片
↓
客户说："我没签字同意这个费用！"
↓
⚠️ 责任不清，产生纠纷
```

**锁定机制解决**：
```
维修人员查看签字照片
↓
系统自动记录并锁定
↓
照片不能被修改
↓
✅ 有锁定时间戳作为证据
✅ 责任明确：维修人员看到的就是客户签字的
✅ 避免纠纷
```

---

### 责任归属表

| 时间点 | 照片状态 | 现场人员责任 | 维修人员责任 |
|-------|---------|-------------|-------------|
| 上传后，查看前 | 未锁定 | ✅ 负责照片准确性 | - |
| 维修人员查看后 | 🔒 已锁定 | ✅ 照片已确定 | ✅ 根据此照片进行维修 |
| 申请修改 | 🔒 已锁定 | ⚠️ 需要说明原因 | - |
| 管理员批准修改 | 解锁 | ✅ 重新负责 | - |

## 🔐 安全性

### 防止绕过锁定

1. ✅ **后端验证**：所有操作都在后端验证
2. ✅ **数据库约束**：通过字段检查锁定状态
3. ✅ **权限控制**：只有指定角色可以操作
4. ✅ **操作记录**：所有操作都有日志

### 防止恶意申请

1. ✅ **必填原因**：申请必须填写详细原因
2. ✅ **申请记录**：所有申请都保存在数据库
